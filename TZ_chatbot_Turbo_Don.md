## 1. Общие сведения

Настоящее техническое задание определяет требования к разработке интеллектуального чат-бота для сайта turbo-don.ru. Чат-бот должен автоматизировать консультации клиентов, подбор оборудования, эксплуатационную поддержку и работу с нормативно-технической документацией в области учета газа, нефти и нефтепродуктов.

| **Параметр** | **Описание** |
|--------------|---------------|
| Наименование системы | Интеллектуальный чат-бот для сайта turbo-don.ru |
| Тип решения | Веб-виджет с LLM-ядром, RAG-базой знаний, сценариями подбора оборудования и интеграциями с внешними системами |
| Основные пользователи | Инженеры и технологи, специалисты закупок, эксплуатационный персонал, сотрудники отдела продаж и технической поддержки |
| Ключевой результат | Снижение времени консультации и подбора оборудования, повышение качества ответов и снижение нагрузки на сотрудников |

## 2. Назначение и цели разработки

Система предназначена для автоматизации клиентского сервиса и повышения эффективности работы отдела продаж за счет использования интеллектуального помощника, отвечающего на вопросы пользователей и сопровождающего их до целевого действия.

- предоставление квалифицированной консультационной помощи по продукции, ее применению и нормативным требованиям;
- автоматизация подбора оборудования по формальному опросному листу или свободному текстовому описанию задачи;
- эксплуатационная поддержка владельцев оборудования ГК «Турбулентность-ДОН»;
- работа в режиме нормативно-справочного помощника по ГОСТам и ведомственным стандартам в области учета газа, нефти и нефтепродуктов;
- формирование лидов, заявок на коммерческие предложения, обращений в техподдержку и сервисные тикеты.

## 4. Область работ и границы проекта

### 4.1. Входит в объем работ

- разработка чат-виджета для размещения на сайте turbo-don.ru;
- создание диалоговых сценариев для консультаций, подбора оборудования, поверки, ремонта и поиска нормативов;
- разработка RAG-пайплайна для поиска по паспортам, руководствам, ГОСТам, ведомственным документам и каталогу продукции;
- интеграция с цифровым каталогом продукции и источниками технической документации;
- интеграция с CRM для создания лидов, сделок или тикетов;

### 4.2. Не входит в объем работ без отдельного согласования

- разработка новой CRM или замена существующих внутренних систем;

- полная миграция каталога продукции, если исходный каталог не содержит структурированных данных;
- поддержка голосовых каналов и телефонии, если это не согласовано отдельным этапом.

### 5.1. Сценарий интеллектуального консультирования

1. Пользователь формулирует вопрос в свободной форме.
2. Система определяет тему вопроса и ищет релевантные источники в базе знаний.
3. LLM формирует ответ только на основании найденных документов и при необходимости задает уточняющий вопрос.
4. В ответе отображаются ссылки на использованные источники, если вопрос связан с нормативами или технической документацией.

### 5.2. Сценарий подбора оборудования

Подбор оборудования должен поддерживать два режима: формальный и свободный. В формальном режиме пользователь проходит последовательный опросный лист. В свободном режиме бот извлекает параметры из естественного языка и при необходимости уточняет недостающие данные.

| **Параметр подбора** | **Описание / пример значения** |
|----------------------|--------------------------------|
| Среда | Газ, жидкость, нефтепродукт, сжиженный газ и другие среды из каталога |
| Температура | Рабочий диапазон температуры процесса |
| Давление | Рабочее и максимальное давление |
| Вязкость | Требуемое значение или диапазон вязкости |
| Точность | Требуемый класс точности или предельная погрешность |
| DN / условный проход | Диаметр трубопровода или присоединительный размер |
| Назначение учета | Коммерческий учет, технологический учет, поверка, эксплуатация |
| Документы | Паспорт, чертеж, руководство по эксплуатации, опросный лист |

### 5.3. Нормативно-справочная функция «Инспектор стандартов»

Функция должна обеспечивать поиск и ответы по нормативной базе. При ответе на вопросы по ГОСТам и ведомственным стандартам бот обязан указывать источник, пункт и страницу, если они доступны в индексированных документах.

| **Группа нормативов** | **Документы для включения в базу знаний** |
|-----------------------|---------------------------------------------|
| Учет газа | ГОСТ 2939-63, ГОСТ Р 8.741-2019, ГОСТ 8.611-2013 |
| Учет нефти и нефтепродуктов | ГОСТ 8.587-2019, ГОСТ 8.589-2007, ГОСТ Р 8.647-2008 |
| Ведомственные стандарты | Инструкции ПАО «Газпром» и ПАО «Транснефть», относящиеся к узлам учета |
| Документация производителя | Технические паспорта, руководства по эксплуатации, чертежи и описания моделей Turbo Flow UFG-H, Turbo Flow UFG-Z, Turbo Flow UFL и других моделей |

## 7. Технологическая архитектура

Для обеспечения ответов по нормативам и оборудованию должна быть реализована архитектура RAG (Retrieval-Augmented Generation), при которой языковая модель формирует ответы на основании документов компании и нормативной базы, а не только на общих знаниях модели.

| **Компонент** | **Назначение** | **Требования** |
|---------------|----------------|----------------|
| Веб-виджет | Клиентский интерфейс на сайте | JavaScript-встраивание, кастомизация под бренд, поддержка быстрых кнопок и файлов |
| Backend API | Обработка диалогов, маршрутизация сценариев, интеграции | REST/GraphQL API или иной согласованный интерфейс, журналирование событий |
| LLM-ядро | Понимание вопросов и генерация ответов | Поддержка GPT-4o, YandexGPT или локальной модели по согласованию; обязательная работа через промпты и контекст из RAG |
| RAG-пайплайн | Поиск релевантных источников | Chunking документов, embeddings, векторная база, гибридный поиск semantic + BM25 |
| База знаний | Хранение паспортов, РЭ, ГОСТов и каталогов | Версионирование документов, метаданные: тип документа, модель, дата, страница, пункт |
| CRM-интеграция | Создание лидов, сделок и тикетов | Передача контактов, параметров подбора, файлов и истории диалога |
| Уведомления | Оповещение сотрудников | Telegram/СБИС или иной согласованный канал для критичных обращений |

### 7.1. Логика обработки запроса

1. Классификация намерения пользователя: консультация, подбор оборудования, сервис/поверка, нормативный вопрос, продажа или иной запрос.
2. Извлечение параметров из сообщения пользователя и истории диалога.
3. Поиск релевантных документов в базе знаний с применением гибридного поиска.
4. Проверка достаточности данных: при нехватке параметров задается уточняющий вопрос.
5. Генерация ответа с указанием источников или формирование заявки/тикета при необходимости.
6. Сохранение обезличенной аналитики диалога и пользовательской оценки качества ответа.

## 8. Требования к данным и базе знаний

Качество работы чат-бота напрямую зависит от полноты и актуальности базы знаний. До запуска необходимо собрать, очистить, структурировать и проиндексировать документы, используемые для ответов.

| **ID** | **Требование** | **Описание** |
|--------|----------------|--------------|
| D-01 | Паспорта и РЭ | Индексировать технические паспорта, руководства по эксплуатации, инструкции по монтажу и обслуживанию оборудования. |
| D-02 | Каталог продукции | Структурировать модели, характеристики, диапазоны измерений, классы точности, ограничения применения и ссылки на документы. |
| D-03 | Нормативная база | Загрузить актуальные редакции ГОСТов и ведомственных документов с метаданными: название, номер, год, пункт, страница. |
| D-04 | Версионирование | При обновлении документа сохранять дату загрузки, источник, версию и статус актуальности. |
| D-05 | Качество чанков | Разбивка должна сохранять смысловые блоки, таблицы и заголовки, чтобы бот корректно цитировал источники. |
| D-06 | Контроль источников | Ответы по нормативам и оборудованию должны строиться по найденным документам; при отсутствии источника бот сообщает о невозможности подтвердить ответ. |

| NFR-01 | Производительность | Типовой ответ по базе знаний должен формироваться за приемлемое для веб-чата время; сложный подбор или поиск норматива должен завершаться без ручного поиска сотрудником. |
| NFR-02 | Надежность | При недоступности LLM, базы знаний или CRM система должна показать понятное сообщение и предложить оставить контакт для связи. |
| NFR-03 | Масштабируемость | Архитектура должна позволять увеличивать объем документов, моделей оборудования и количество одновременных диалогов. |
| NFR-04 | Поддерживаемость | Диалоговые сценарии, промпты и база знаний должны обновляться без переразвертывания всего сайта. |
| NFR-05 | Наблюдаемость | Должны быть доступны логи, метрики качества поиска, оценки пользователей и статистика эскалаций. |
| NFR-06 | Качество ответов | В ответах по техническим и нормативным вопросам должны отсутствовать неподтвержденные утверждения при наличии требования цитирования. |
| NFR-07 | Совместимость | Виджет должен корректно работать в актуальных версиях основных браузеров и на мобильных устройствах. |

## 12. Метрики эффективности

| **Метрика** | **Целевое значение** | **Метод измерения** |
|-------------|----------------------|----------------------|
| CSAT | > 85% положительных оценок по результатам голосования после сессии | Оценка пользователя в конце диалога |
| TTR по типовым задачам | Сокращение времени решения задачи подбора норматива или модели до 30 секунд | Сравнение времени обработки до и после внедрения |
| Доля автоматических ответов | Определяется на пилотном этапе | Отношение закрытых ботом диалогов к общему числу обращений |
| Доля успешных эскалаций | 100% критичных обращений должны попадать ответственному сотруднику | Проверка CRM и канала уведомлений |
| Качество цитирования | Ответы по нормативам должны содержать корректный источник | Тестовый набор вопросов и экспертная проверка |
